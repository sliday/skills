# Start with the job

Help the client create something a user can try and a design or development team can continue. Preserve their product idea, stack preferences and constraints. Do not turn an example into a required architecture.

Identify:

- The specific user and situation.
- The task they need to finish, including the starting trigger and useful result.
- Their current workaround.
- The assumption that could make the product unnecessary or unusable.

Use what the client supplied. Ask only for missing information that changes the prototype. When they want you to proceed, state tentative assumptions and choose a reversible default. Do not invent customers, interviews, market demand or approval.

Write a short direction statement: “For [user] in [situation], help them [task] so they can [result]. We need to learn whether [risky assumption].” Describe one observable task that could challenge that assumption. Keep the promised learning within what a prototype can show: a clickable flow can test understanding; it cannot prove demand, safety, production reliability or revenue.

Choose the deliverable to match available tools:

- With file and execution tools, build a runnable artifact in the client's chosen environment and verify what you can run.
- With a preview or artifact tool, create an interactive flow there and state its limits.
- In a conversational interface, guide the user through a screen-by-screen simulation, then provide a prototype brief and copyable implementation instructions. Call this a simulation or brief, not a working application.

Leave the client with the direction statement, the first task to prototype, the main assumption and the proposed exclusions. Continue into implementation when authorized; do not stop at a plan if your tools can produce the requested artifact. Avoid global installs, billing setup and external publishing unless the client requests them.
